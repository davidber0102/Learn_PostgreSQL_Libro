---------------------------------------------------------------------------------------
		- Para poder interactuar con una base de datos en el clúster, debe tener al menos un usuario.
		- Un único usuario administrador (denominado postgres)
		- Es mejor crear diferentes usuarios con diferentes propiedades y privilegios
		- Estructura de administración de usuarios muy rica
--- Introducción a los usuarios y grupos
		- Para poder acceder y conectarse de forma interactiva con un base de datos alamacenada en postgresql, se debe tener credeneciales de inicio de sesion
		- ademas de contar con los permisos para poder conectarse a una base en especifico
		- Son similares cuando accedes a un sistema operativo (nombre de ususario y contraseña)
		- Un rol puede ser una cuenta o un grupo de cuentas o ambas.
		- Cada rolo debe tener un nombre unico, nombre de usuario.
		- Un rol es la agrupacion de permisos a una base de datos.
		- Un rol se define a nivel de cluster, unico nombre dentro de todo el cluster
--- Gestión de roles
		- Se puede pueden administrar mediante tres declaraciones SQL principales:
			- CREATE ROLE para crearun rol desde cero
			- ALTER ROLE para cambiar algunas propiedades del rol (por ejemplo, la contraseña deinicio de sesión)
			- DROP ROLE para eliminar un rol existente.
		- El rol de superusuario postgres en un inicio puede usarse para ejecutar cestas consultas
		- El nombre del rol debe ser único en todo el sistema, lo que significa que no puede tener dos roles diferentes con nombres idénticos, y debe constar de letras, dígitos y algunos símbolos, como guiones bajos.
	-- Creando nuevos roles
			- Se debe ocupar lo siguiente CREATE ROLE y tiene la siguiente sinopsis y requiere parametros obligatorios que en este caso el es nombre de usuario del rol
				+ CREATE ROLE name [ [ WITH ] option [ ... ] ]
					- Delcaracion de contraseña
					- Delcaracion de capacidad de inicio de sesiosn
					- Delcaracion de privilegios de superusuario.
			- Recuerde que en postgresql se puede tener tantos superusuarios como desse.
			- Una ves creado el usuari o rol, y por algun motivo se dbe cambiar alguna opcion del rol ya creado
				- Interviene ALTER ROLE
					- permite (como superusuario del clúster) modificar un rol existente sin tener que descartarlo y volver a crearlo.
		-- Contraseñas de roles, conexiones y disponibilidad
			- La conexion mediante un usuario/rolm es mediante autentificasion en postgresql.
			- Principales opciones que el porgrama permite manipular y admonostrar para el inicio de sesion
				- PASSWORD or ENCRYPTED PASSWORD: lmacena contraseñas de roles en forma cifrada,
				- PASSWORD NULL: fuerza explícitamente una contraseña nula (no vacía), lo que impide que el usuario inicie sesión con cualquier contraseña.
				- CONNECTION LIMIT <n>: permite al usuario abrir no más de <n> conexiones simultáneas al clúster
				- VALID UNTIL: le permite especificar un instante (en el futuro) en el que caducará el rol.
			- La siguiente sentencia crea un rol, con su contraseña pero no permitira que inicio sesion en el cluster	
				+ CREATE ROLE luca WITH PASSWORD 'xxx';
				- La opción predeterminada es NOLOGIN
			- Sin encambio para definiri usuarios interactivos, recuerde agregar la opcion LOGIn al momneto de crear el usuario/rolm
				+ CREATE ROLE luca WITH LOGIN PASSWORD 'xxx';
			- la siguiente sentencia es similiar a ala anterior, se puede escribir de varias formas y en cualquier orden
				+ CREATE ROLE luca WITH PASSWORD 'xxx' LOGIN;
			- VALID UNTIL definir una fecha o incluso una marca de tiempo y que permitira caducará la contraseña del rol y ya no se le permitirá iniciar sesión en el clúster
				+ CREATE ROLE luca WITH LOGIN PASSWORD 'xxx' VALID UNTIL '2020-12-25 23:59:59';
	-- Uso de un rol como grupo
		- Un grupo es un rol que contiene otros roles.
		- Para crear un GRUPO es necesario:
			- crear un rol sin la opción LOGIN y luego agregar todos los miembros uno tras otro
		- IN ROLE: se debe incluir en la sentencia para crear un rol como miembro de un grupo especifico
			+ CREATE ROLE book_authors WITH NOLOGIN;
			+ CREATE ROLE luca WITH LOGIN PASSWORD 'xxx' IN ROLE book_authors;
			+ CREATE ROLE enrico WITH LOGIN PASSWORD 'xxx'IN ROLE book_authors;
		- GRANT: agregar miembros a un grupo
			- GRANT ROLE book_authors TO enrico;
		- Cada grupo puede tener uno o más miembros administradores
		- ADMIN: Permite a un usuario especificar el miembro que se asociará como administrador del grupo recién creado
			+ CREATE ROLE book_reviewers WITH NOLOGIN ADMIN luca;
		- WITH ADMIN OPTION: permite la pertenencia a un rol con privilegios administrativos.
			+ GRANT book_reviewers TO enrico WITH ADMIN OPTION;
	-- Eliminación de un rol existente
		- DROP ROLE: eliminar un rol existente
			+ DROP ROLE [ IF EXISTS ] name [, ...]
		- Para ser eliminado, el rol debe existir; por lo tanto, si intenta eliminar un rol inexistente, recibirá un error:
			+ DROP ROLE this_role_does_not_exists;
			+ ERROR: role "this_role_does_not_exists" does not exist
		- ¡PostgreSQL se protegerá de sus errores y hace un muy buen trabajo al mantener sus datos seguros!
			+ DROP ROLE + IF EXISTS mpide que PostgreSQL se queje de la eliminación de un rol que falta:
				+ DROP ROLE IF EXISTS this_role_does_not_exists;
				+ NOTICE: role "this_role_does_not_exists" does not exist, skipping  DROP ROLE
					-muestra un aviso sobre el  hecho de que el rol no existe
				+ IF EXISTS: La idea es evitar reportar un error cuando no está interesadoen detectarlo
		- eliminar un grupo no afecta a sus miembros
	-- Inspeccionar roles existentes
		- Hay diferentes formas de obtener información sobre los roles existentes y todas se basan en los catálogos de PostgreSQL
			+ SELECT current_role;
		- El comando \du nos ayuda a obtener información sobre los roles existentes y sus propiedades
			+ SELECT * FROM pg_roles;
		- En la columna Login, se puede observar si se impide que un rol se conecte de forma interactiva al clúster
		- Puede obtener información sobre un rol específico consultando directamente el catálogo pg_roles
			+ SELECT rolname, rolcanlogin, rolconnlimit, rolpassword FROM pg_roles WHERE rolname = 'luca';
				- contraseña no se muestra por razones de seguridad siempre se almacenan encriptadas.
		- pg_authid representa la columna vertebral de la información de pg_roles y se puede consultar con la misma declaración, pero informa la contraseña del usuario (como texto encriptado).
			+ SELECT rolname, rolcanlogin, rolconnlimit, rolpassword FROM pg_authid WHERE rolname = 'luca';
			- La contraseña se representa como un hash y la parte inicial especifica el algoritmo de cifrado utilizado: MD5.
--- Administrar las conexiones entrantes a nivel de rol
	- para la propiedad LOGIN  al crear un rol no es suficiente para que abra una nueva conexión a cualquier base de datos dentro del clúster
	- PostgreSQL verifica la solicitud de conexión entrante con una especie de tabla de firewall,
	- Cada modificacion realizadan dentro del archivo pg_hba.conf , se debe indicar que el cluster vuelva a cargar nuevas reglas atraves de l reinicio del serivicio
	- Esto se define dentro del archivo pg_hba.conf
		+ En linux $ sudo -u postgres pg_ctl reload -D $PGDATA
		+ En windows ir a los Servicios del sistema, buscar y localizar el correspondiente  a postgresql y reiniciar 		
		-- La sintaxis de pg_hba.conf
			- El archivo pg_hba.conf contiene el cortafuegos para las conexiones entrantes
			- La estructura dentro del archivo es la siguiente:
				+ <connection-type> <database> <role> <remote-machine> <auth-method>
			- <connection-type> 
			- <database> conexión compatible con PostgreSQL : 
				* 1- local: a través de sockets del sistema operativo
				* 2. host: conexión TCP/IP
				* 3. hostssl: conexión cifrada TCP/IP
			- <role> 
			- <remote-machine> 
			- <auth-method>
				
		-- Orden de reglas en pg_hba.conf
		-- Fusión de varias reglas en una sola
		-- Uso de grupos en lugar de roles individuales
		
		-- Uso de archivos en lugar de roles individuales
